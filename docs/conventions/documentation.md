# 문서 작성 및 유지 관리 규약

`docs/`에 문서를 작성·수정·삭제할 때 따른다.

작고 정확한 문서 집합을 많은 문서보다 우선한다. 문서는 코드와 함께 갱신하며,
더 이상 유효하지 않은 문서는 보관하지 않고 삭제한다.

이 규약은 Google의
[Documentation Best Practices](https://google.github.io/styleguide/docguide/best_practices.html)를
참고한다.

## 1. 새 문서 생성 판단

새 문서를 만들기 전에 다음 순서로 판단한다.

### 1.1 기존 문서로 해결할 수 있는가

기존 문서의 목적을 해치지 않고 내용을 추가할 수 있다면 새 문서를 만들지 않고
기존 문서를 수정한다.

관련 내용이 다른 문서에 이미 있다면 내용을 복사하지 않고 해당 문서를 연결한다.

기존 문서에 넣으면 서로 다른 목적의 내용이 섞이거나 문서가 지나치게 커진다면
다음 단계로 진행한다.

### 1.2 코드나 기존 관리 수단으로 충분히 설명되는가

다음 위치 중 하나가 필요한 정보를 충분히 제공한다면 별도 문서를 만들지 않는다.

- 코드와 docstring
- 테스트
- FastAPI가 생성한 OpenAPI
- GitHub 이슈와 PR
- 기존 README 또는 규약 문서

정확한 요청·응답 필드와 제약은 OpenAPI에 반영한다.
작업 상태, 담당자, 일정과 논의 과정은 GitHub 이슈나 PR에 기록한다.
코드에서 명확하게 드러나는 구현 세부는 코드에 둔다.

이것만으로 구현 기준이나 업무 규칙을 설명하기 어렵다면 다음 단계로
진행한다.

### 1.3 독자와 문서의 목적이 분명한가

다음 두 문장을 구체적으로 작성할 수 있어야 한다.

- 이 문서를 읽어야 하는 사람은 누구인가
- 그 사람이 이 문서를 읽고 어떤 작업이나 판단을 할 수 있어야 하는가

두 문장을 작성할 수 없다면 새 문서를 만들지 않는다. 먼저 GitHub 이슈나 PR에서
문서가 필요한 이유와 전달할 정보를 구체화한 뒤 다시 판단한다.

두 문장이 분명하다면 새 문서를 만들 수 있다.

## 2. 최소한의 실행 가능한 문서화

문서는 독자가 작업하거나 판단하는 데 필요한 최소한의 정보만 담는다.

다음 내용은 작성하지 않는다.

- 코드에서 바로 알 수 있는 함수·클래스·파일의 동작
- OpenAPI가 생성하는 요청·응답 필드와 제약의 반복
- 작업 진행 상태, 담당자와 일정
- 구현 과정에서만 필요한 짧은 메모
- 다른 문서의 내용을 복사한 설명
- 결론이나 구현 기준에 영향을 주지 않는 긴 배경
- 실제로 검토하지 않은 가상의 확장 가능성과 예외 상황

배경은 결정 이유를 이해하는 데 필요한 만큼만 작성한다.
예시는 규칙을 설명하는 데 필요할 때만 대표 사례를 작성한다.

문서를 더 완전하게 만들기 위해 범위를 넓히기보다, 현재 필요한 내용을 먼저
정확하게 작성한다.

## 3. 코드와 함께 문서를 갱신한다

코드 변경으로 기존 문서의 설명이 달라지면 같은 PR에서 문서를 함께 수정하거나
삭제한다.

다음 변경은 관련 문서 갱신을 포함한다.

- API 경로, 요청·응답 형식과 오류 계약 변경
- 비즈니스 규칙과 처리 흐름 변경
- 설정 항목과 기본값 변경
- 디렉터리 구조와 실행·테스트 절차 변경
- 보안, 개인정보와 로그 정책 변경
- 기존 기능이나 코드 제거

코드와 문서가 서로 다른 상태를 설명하면 작업이 완료된 것으로 보지 않는다.

API의 정확한 요청·응답 명세는 OpenAPI를 단일 출처로
사용한다. 스펙 문서는 OpenAPI만으로 설명하기 어려운 업무 규칙, 처리 흐름과
설계 결정을 다룬다.

문서만 변경하는 경우에도 현재 코드와 테스트를 기준으로 내용이 맞는지 확인한다.

## 4. 죽은 문서를 삭제한다

다음 중 하나에 해당하는 문서는 삭제한다.

- 제거된 기능이나 더 이상 지원하지 않는 계약을 설명한다
- 다른 문서나 코드가 완전히 대체했다
- 현재 구현과 충돌하며 다시 유효해질 계획이 없다
- 완료된 일회성 마이그레이션·정리 계획만 담고 있다
- 동일한 정보의 단일 출처가 다른 위치에 있다
- 내용이 없어도 개발·운영·검토에 영향을 주지 않는다

삭제 대상 문서를 `archive/`, `deprecated/` 같은 디렉터리로 옮겨 보관하지 않는다.
필요하면 Git 기록과 관련 이슈·PR에서 과거 내용을 확인한다.

문서의 일부만 유효하다면 필요한 내용을 현재 문서에 반영한 뒤 기존 문서를
삭제한다.

문서를 삭제할 때는 저장소 안에서 해당 문서를 연결하는 위치를 검색해 함께
수정한다.

## 5. 스펙 문서

스펙 파일은 내용을 나타내는 `<짧은-설명>.md` 형식으로 이름을 짓는다.
스펙은 GitHub 이슈와 독립적으로 작성하며, 특정 이슈 번호나 진행 상태를 본문과
파일 이름에 넣지 않는다. 구현에 스펙이 필요하면 GitHub 이슈에서 스펙 문서를
링크한다.

파일명과 첫 번째 제목만 보고도 검색 결과에서 문서의 대상을 빠르게 구분할 수 있게
작성한다. 파일명에는 대상과 핵심 내용을 드러내고, 첫 번째 제목에는 이 업무의
핵심 설명을 한국어 한 문장으로 적는다.

`핵심 결정`은 결정별로 `-` 목록 기호를 사용해 작성한다. 각 항목에는 선택한
내용과 필요한 근거를 함께 적어 결정 사항을 빠르게 훑을 수 있게 한다.

`상세 설계`는 구조, 흐름, 데이터, 오류 처리처럼 큰 주제별로 `###` 제목 아래에
내용을 묶는다. 제목만 훑어도 문서 구조를 파악할 수 있도록 각 제목에 다루는
내용을 구체적으로 드러낸다.

### 5.1 기본 형식

```markdown
<!-- 한국어로 이 업무의 설명을 한 문장으로 핵심만 적는다. -->
# <작업 제목>

## 1. 핵심 결정

- <구현 전에 합의해야 하는 주요 선택과 그 근거>
- <서로 구분되는 결정은 별도 항목으로 작성>

## 2. 상세 설계

### 2.1 <큰 주제>

<코드와 OpenAPI만으로 설명하기 어려운 설계 내용>

### 2.2 <큰 주제>

<구조, 흐름, 데이터, 업무 규칙과 오류 처리 등을 주제별로 작성>
```

문서의 목적을 달성하는 데 필요하지 않은 섹션은 추가하지 않는다.

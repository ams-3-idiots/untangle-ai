# Git 규약

브랜치를 만들 때, GitHub 이슈를 작성·수정할 때, 이슈에 연결할 스펙 문서를 쓸 때,
커밋할 때, PR을 올릴 때 읽는다.

- 커밋을 생성하기 전 사용자 검토 절차는 `AGENTS.md`의 [4. 커밋 전 사용자 검토](../../AGENTS.md#4-커밋-전-사용자-검토)를 따른다.

## 0. 목차

1. [Git Branch](#1-git-branch) — 브랜치 구분, 이름, 분기 기준과 PR 대상
2. [GitHub Issue](#2-github-issue) — 본문 구성과 문체, 스펙 문서
3. [Git Commit](#3-git-commit) — 접두어와 메시지 작성
4. [GitHub PR](#4-github-pr) — 제목·본문 구성과 문체

## 1. Git Branch

### 1.1 구분

| 구분 | 사용 | 예 |
| --- | --- | --- |
| `feature` | 기능 추가·변경 | `feature/document-upload-api` |
| `bugfix` | 버그 수정 | `bugfix/token-refresh-race` |
| `hotfix` | 바로 반영해야 하는 긴급 수정 | `hotfix/security-patch` |
| `release` | 릴리스 준비 | `release/v1.2.0` |
| `chore` | 의존성·설정·빌드·문서·구조 개선 등 그 외 | `chore/update-dependencies` |

- 브랜치 구분은 3번의 커밋 접두어와 별개 체계다.
  같은 값을 쓰려고 맞추지 않는다.
  예를 들어 `chore/split-user-service` 브랜치의 커밋 제목은 `refactor: ...`가 된다.

### 1.2 이름

- `<구분>/<짧은-설명>` 형식이며 영어 소문자와 하이픈으로 작성한다.
- GitHub 이슈가 있는 작업은 `<구분>/<이슈-번호>-<짧은-설명>` 형식을 쓴다.
  번호는 GitHub가 발급한 값만 사용하며 저장소 문서를 보고 직접 배정하지 않는다.
- `release`만 `release/<버전>` 형식을 쓴다.

### 1.3 분기 기준

- 사용자가 따로 명시하지 않았다면 브랜치는 최신 `main`에서 분기한다.

### 1.4 PR 대상 브랜치

- 작업 브랜치의 PR은 `main`을 대상으로 보낸다.

## 2. GitHub Issue

- `gh` CLI를 사용하여 작업한다.

### 2.1 본문 구성

`.github/ISSUE_TEMPLATE/feature.md`의 섹션과 순서를 그대로 사용한다.

| 섹션 | 내용 |
| --- | --- |
| `의존 관계` | 선행·후속 이슈 번호. 없으면 `없음` |
| `목적` | 작업으로 달성할 결과와 필요한 이유 |
| `배경` | 현재 상태, 문제 상황과 관련 맥락 |
| `범위` | 구현·변경할 내용과 이번 작업에서 제외할 내용 |
| `작업 계획` | 주요 작업 단위를 수행 순서대로 정리 |
| `예상 변경 영역` | 디렉터리나 주요 파일과 해당 위치의 예상 작업 |
| `관련 스펙 문서` | 연결된 스펙 문서 경로. 없으면 `없음` |
| `참고` | 관련 문서, 로그, 화면과 기존 PR |

- `목적`과 `배경`을 포함한 설명은 목록으로 작성한다.
- 제외 범위는 `### 제외` 밑에 리스트로 작성한다.
- `예상 변경 영역`은 `<경로>: <예상 작업>` 형식으로 작성한다.
- 상세 계약과 구현 결정은 관련 스펙 문서에 작성하고 이슈에서 연결한다.

### 2.2 문체

- 본문은 개조식으로 작성한다.
- `~다`로 끝나는 서술형 문장 대신 `구현`, `연결`, `검증`, `제외`, `필요`처럼
  짧은 명사형이나 동사형 표현을 사용한다.
- 작업한 사람만 아는 맥락과 모호한 약어를 피하고 처음 읽는 팀원이 이해할 수 있게 쓴다.
- 한 줄이 길어지면 100자 안팎에서 끊는다.

### 2.3 스펙 문서

`docs/specs/`에는 코드와 이슈 본문만으로 범위와 계약을 설명하기 어려운 작업의
상세 구현 스펙을 둔다.

- 모든 GitHub 이슈에 스펙 문서를 만들 필요는 없다.
- 이슈와 연결한 스펙 파일은 `<이슈-번호>-<짧은-설명>.md` 형식을 사용한다.
  번호는 GitHub가 발급한 값만 사용하며 직접 배정하지 않는다.
- 번호가 붙은 스펙 문서는 같은 번호의 GitHub 이슈 하나와 대응한다.
- 작업 상태, 담당자, 이슈 간 의존 관계와 진행 중인 논의는 GitHub 이슈에서 관리한다.
- 작업의 목적, 범위와 계획은 GitHub 이슈에서 관리한다.
- 구현에 영향을 주는 핵심 결정과 상세 설계는 스펙 문서에서 관리한다.

#### 스펙 문서 템플릿

스펙 문서는 다음 두 섹션을 기본 틀로 사용한다.

```markdown
# <작업 제목>

> 관련 GitHub Issue: [#<이슈 번호>](<이슈 URL>)

## 1. 핵심 결정

<구현 전에 합의해야 하는 주요 선택과 그 근거>

## 2. 상세 설계

<구조, 흐름, 인터페이스, 데이터와 오류 처리 등 구현 기준>
```

- `핵심 결정`과 `상세 설계`의 하위 섹션은 작업 내용에 맞게 구성한다.

## 3. Git Commit

### 3.1 제목
- `접두어: <메시지>` 형식
- 접두어는 아래 표를 참고하고, 메시지는 한국어로 작성

| 접두어 | 사용 |
| --- | --- |
| `feat` | 기능 추가·변경 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 (`docs/`, `README`, `AGENTS.md`, `CLAUDE.md`) |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 의존성·설정·빌드 등 (`pyproject.toml`, `uv.lock`, `Dockerfile`, `.env.example`, CI 설정) |

### 3.2 본문

- 제목은 요약형으로 한 줄. 바뀐 코드 중에 가장 중요하다고 생각하는 변경 사항이 드러나게 적는다.
- 본문은 전부 한국어로 쓰고, 제목과 한 줄 띄운다.
- 본문 첫 문단에 이 변경이 왜 필요했는지를 한두 문장으로 적는다.
  제목만으로 이유가 분명하면 생략한다.
- 그 아래 한 줄 띄우고, 무엇을 했는지 `-` 목록으로 적는다.
  세부 내용이 필요하면 들여써서 하위 항목으로 적는다.
- 목록 항목은 코드를 열지 않아도 이해되는 단위로 쓴다.
  **바뀐 파일 목록은 적지 않는다.** `git show`가 이미 보여준다.
- 한 줄이 길어지면 40~50자 안팎에서 끊는다.

### 3.3 예시

**`feat` — 기능 추가**

```
feat: 문서 업로드 API 엔드포인트 추가

분석 대상 파일을 서버에 올릴 방법이 없어 분석 흐름을 시작할 수 없었다.

- `POST /documents`로 멀티파트 업로드를 받아 오브젝트 스토리지에 저장한다
- 업로드한 파일의 메타데이터를 `documents` 테이블에 기록한다
- 용량과 허용 확장자를 검증해 초과 시 413/415로 응답한다
```

**`fix` — 버그 수정**

```
fix: 액세스 토큰 갱신 시 동시 요청 경합 수정

만료 직전 요청이 동시에 들어오면 리프레시 토큰이 중복 사용돼
사용자가 401로 로그아웃되는 문제가 있었다.

- 갱신 구간에 사용자 단위 락을 걸어 동시 갱신을 직렬화한다
- 회전 직후 짧은 유예 시간 동안은 이전 토큰 재사용을 허용한다
```

**`docs` — 문서 변경** (제목에서 이유가 분명해 첫 문단을 생략한 예)

```
docs: README에 로컬 개발 환경 구성 방법 추가

- `uv sync`로 의존성을 설치하고 개발 서버를 실행하는 순서를 정리한다
- DB 컨테이너 기동과 마이그레이션 적용 절차를 추가한다
- 환경 변수 예시를 함께 적는다
```

**`refactor` — 구조 개선**

```
refactor: 엔드포인트의 DB 접근 코드를 repository로 분리

엔드포인트가 쿼리를 직접 실행해 커밋 시점이 여러 곳에 흩어져 있었다.

- 조회 쿼리를 `user_repository`로 옮긴다
- 엔드포인트는 서비스만 호출하도록 정리한다
- 커밋은 서비스에서 한 번만 수행한다
```

**`chore` — 의존성·설정·빌드** (항목별 이유를 하위 항목으로 붙인 예)

```
chore: 의존성 및 Docker 빌드 설정 정리

- 미사용 패키지를 제거하고 남은 의존성을 최신 버전으로 업데이트한다
- Dockerfile을 멀티스테이지로 나눈다
  - 런타임 이미지에 빌드 도구가 함께 들어가 크기가 불필요하게 컸다
- `pyproject.toml`과 `uv.lock`을 동기화한다
```

## 4. GitHub PR

- `gh` CLI를 사용하여 작업.
- PR을 보낼 대상 브랜치는 [1.4](#14-pr-대상-브랜치)을 따른다.

### 4.1 제목
- [`브랜치 접두어`] `한 줄 설명`
- `브랜치 접두어`: 작업 브랜치의 구분을 그대로 사용 ([1.1](#11-구분))
- `한 줄 설명`: 수행한 일을 간단하게 한 줄로 서술

### 4.2 본문 구성

`.github/pull_request_template.md`의 네 섹션을 그대로 사용한다.
웹에서 PR을 만들면 이 템플릿이 자동으로 채워지고, `gh`로 만들 때는 같은 구성을 직접 맞춘다.

| 섹션 | 내용 |
| --- | --- |
| `관련 이슈` | `Closes #<번호>`(병합 시 자동 종료) 또는 `Refs #<번호>`(자동 종료하지 않음) |
| `변경 사항 요약` | 구현 결과를 2~4개 항목으로. 파일 목록이 아니라 사용자 동작이나 시스템 동작의 변화를 쓴다 |
| `구현 방식과 주요 결정` | 핵심 구현 방식과 이번 범위에서 뺀 것 |
| `영향 범위와 주의사항` | 호환성·성능·보안, DB·API 변경 여부, 배포 순서와 환경 변수 추가 여부 |

- 이번 PR이 닫는 이슈만 적는다. 상위 이슈와 후속 이슈는 적지 않는다.
- **변경된 모든 내용을 적는 게 목표가 아니다.** 리뷰어가 알아야 할 것만 남긴다.
- 해당 사항이 없는 섹션은 지운다.

### 4.3 문체

- 개조식으로 쓰고 `~다`로 끝나는 서술형 문장을 쓰지 않는다.
  짧은 명사형이나 동사로 끝낸다: `~통일`, `~변환`, `~준비`, `~제외`, `~없음`, `~필요`.
- 작업한 사람만 아는 맥락과 내부 구현 세부는 뺀다. 처음 읽는 팀원이 이해할 수 있게 쓴다.
- `파괴적 변경`처럼 단정적인 평가 대신 무엇이 어떻게 바뀌는지 사실만 적는다.
- 한 줄이 길어지면 100자 안팎에서 끊는다.

### 4.4 예시
```
제목: [feature] Spring 호환 오류 응답·요청 추적·공통 스키마 구현

## 관련 이슈

- Closes #17

## 변경 사항 요약

- AI API의 모든 오류 응답을 Spring과 같은 RFC 9457 ProblemDetail 본문으로 통일.
  FastAPI가 자동으로 만들던 `422` 본문도 같은 형식으로 변환
- 모든 응답에 `X-Request-Id`를 싣고 같은 값을 서버 로그에 기록. 앱이 버그 리포트에
  이 헤더 값을 첨부하면 해당 요청의 로그를 바로 조회 가능
- `Authorization` 헤더의 유무나 값과 무관하게 처리 결과 동일

## 구현 방식과 주요 결정

- 전역 예외 핸들러가 `DomainError`와 요청 검증 실패를 ProblemDetail로 변환.
  서비스는 `HTTPException` 없이 도메인 예외만 발생
- `X-Request-Id`는 미들웨어에서 처리. 요청 성공, 오류 종료, 예상하지 못한 500까지
  모든 응답에 헤더 부착
- 레거시 `/api/v1/ai/*`가 쓰는 `400`·`502` 도메인 예외는 이번 범위에서 제외

## 영향 범위와 주의사항

- **API 호환성**: 오류 응답 본문이 `{"code", "message"}`에서
  `{"type", "title", "status", "detail"}`로 변경. 기존 `code` 값을 읽던 클라이언트는 수정 필요
- **환경 변수 추가**: `LOG_LEVEL` (기본값 `INFO`). 없어도 기본값으로 동작하므로 배포 순서 제약 없음
- **DB 변경 없음**: 테이블·마이그레이션 변경 없음
```

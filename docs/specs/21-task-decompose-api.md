# 할 일 쪼개기 API 호환

> 관련 GitHub Issue: [#21](https://github.com/ams-3-idiots/untangle-ai/issues/21)

## 1. 핵심 결정

### 1.1 전체 흐름

```text
[쪼갤 할 일 한 건 지정]
  ↓
[지정한 할 일로 쪼개기 시작 요청]
  ↓
[새 쪼개기 세션 생성]
  ↓
<어떻게 쪼개 달라는 요청이 있는가?>
  ├─ 있음   → (A) 서브 테스크 생성
  └─ 없음   → (B) 추가 정보 판단

(B) <추가 정보가 필요한가?>
  ├─ 아니요 → (A)
  └─ 예     → <사용자에게 추가 질문을 5회나 했는가?>
                ├─ 예     → (A)
                └─ 아니요 → [추가 질문과 선택지 반환]
                               ↓
                             [사용자 답변 전송]
                               ↓
                             [세션에 저장된 대화에 새 답변 추가]
                               └─↺ (B)

(A) [AI가 할 일 1~5개 생성]
      ↓
(C) [대상을 대체할 전체 목록 반환]
      └─ 같은 세션에서 전체 결과를 더 잘게 요청
           ↓
         [AI가 직전 분해 결과를 기준으로 전체 목록 재구성]
           └─↺ (C)
```

### 1.2 결정 사항

- `sessionId`는 서버가 저장된 질문·답변과 이전 분해 결과를 찾아 후속 요청을
  이어갈 때 사용한다.
- `proposalId`는 앱과 로그에서 질문 또는 분해 응답이 어느 세션의 결과인지
  식별할 때 사용하며, `sessionId`와 항상 같다.
- `items`의 null 여부로 질문 턴과 분해 턴을 구분한다. `firstStep` 필드는
  언제나 null이다.
- 질문은 대화 전체에서 최대 5회다. 5회 도달 후에는 서버가 분해 턴을
  구조적으로 강제한다.
- 앱은 대화 이력을 관리하지 않고 매 턴 이번 발화 하나만 보낸다 — 대화는 서버
  세션이 보관·복원한다.
- 쪼개기 이어가기는 쪼개기 시작으로 만들어진 세션에서만 동작한다.
- 대화는 문자열 아카이브가 아니라 대상 스냅샷·질문 답변 이력·직전 분해 결과로
  나눠 보관하고, 매 턴 하나의 모델 입력으로 재구성한다.
- 질문 횟수는 세션에 센 값으로 판단한다 — 실패한 턴은 세지 않는다.
- 사용자 입력은 마스킹 경계인 모델 입력 본문으로만 보내고 지시문에는 싣지 않는다.
- 시작은 세션을 먼저 만들고, 모델 호출이 성공한 턴만 대화에 저장한다.

## 2. 상세 설계

### 2.1 시작 요청

`POST /api/v1/ai-sessions/decompose` → `201` (세션을 직접 생성해 반환 — 별도
세션 생성이 필요 없다)

```json
{
  "target": { "title": "운동 시작하기", "notes": null },
  "instruction": null
}
```

| 필드 | 설명 | 필수 | 제약 |
| --- | --- | --- | --- |
| `target` | 쪼갤 할 일 | 필수 | 객체 |
| `target.title` | 쪼갤 할 일의 제목 | 필수 | 비공백, 최대 500자 |
| `target.notes` | 대상에 대한 보충 메모 | 선택 | 최대 4000자 |
| `instruction` | 분해 방식 지시 — 있으면 질문 없이 바로 분해한다 | 선택 | 최대 2000자 |

### 2.2 이어가기 요청

`POST /api/v1/ai-sessions/{sessionId}/decompose` → `200`

```json
{ "message": "체력 증진이 목적이야" }
```

| 필드 | 설명 | 필수 | 제약 |
| --- | --- | --- | --- |
| `message` | 이번 턴의 사용자 발화 — 선택지 칩 텍스트 또는 자유 입력 | 필수 | 비공백, 최대 2000자 |

### 2.3 응답 (시작·이어가기 공통) — `items`의 null 여부로 턴 구분

```json
{
  "sessionId": "cace6837-…",
  "proposalId": "cace6837-…",
  "items": null,
  "options": ["체중 감량", "체력 증진", "스트레스 해소"],
  "firstStep": null,
  "assistantText": "운동을 시작하려는 주된 목적이 뭔가요?"
}
```

| 필드 | 질문 턴 | 분해 턴 |
| --- | --- | --- |
| `items` | **null** | `TaskDraft` 배열 1~5개, 배열 순서 = 실행 순서 |
| `options` | 선택지 2~4개 | **null** |
| `firstStep` | null | null |
| `assistantText` | AI의 질문 한 문장 | 한두 문장 설명 |
| `sessionId`·`proposalId` | 항상 존재, 같은 값 | 항상 존재, 같은 값 |

- **`firstStep` 필드는 유지하되 값은 언제나 null이다.** '지금 할 첫 단계'는
  `items[0]`으로 온다. 분해 턴의 `items`가 비어 있는 모델 응답은 `503`으로
  처리한다.
- 질문 턴의 조건: `assistantText`가 비공백이고 중복 제거 후 `options`가 2개
  이상. 선택지는 최대 4개까지만 내려보낸다.
- 질문은 대화 전체에서 최대 5회다. 질문 턴 5회에 도달하면 이후 응답은 반드시
  분해 턴이다.
- 분해 턴을 받은 뒤에도 같은 세션에 "더 잘게 쪼개줘"를 보내면 서버가 직전
  목록을 기억하고 전체를 더 잘게 재구성해 돌려준다(항목 수 상한 5개 동일).
- "그냥 쪼개줘"·"모르겠어" 같은 발화에는 즉시 분해로 넘어간다.
- 쪼개기 시작 기록이 없는 세션(세션 생성 API로 만든 세션 등)에 이어가기를
  호출하면 `404`다.

`TaskDraft`의 공통 정의와 정규화 규칙은
`docs/specs/17-spring-compatible-http-base.md`를 따르고, 쪼개기에서는 다음
규칙을 더한다.

| 필드 | 쪼개기 규칙 |
| --- | --- |
| `memo`·`dueDate`·`dueTime`·`reminderMinutesBefore` | **항상 null** |
| `importance`·`estimatedMinutes` | 모델 제안 — 정규화로 null이 될 수 있음 |
| `sourceExcerpt` | **항상 대상 제목** (개행을 공백으로 접고 앞뒤 공백을 없앤 `target.title`) |

### 2.4 세션에 보관하는 대화 상태

`docs/specs/18-ttl-session-idempotency.md`의 TTL 세션에 다음을 보관하고 다음 턴에서
복원한다. 모델 호출과 응답 조립이 모두 성공한 턴만 저장하므로, 실패한 턴은 대화를
바꾸지 않는다.

| 항목 | 내용 |
| --- | --- |
| 대상 제목·메모·지시 | 시작 요청의 스냅샷. 제목은 한 줄로 접어 저장한다 |
| 질문 횟수 | 지금까지 돌려준 질문 턴의 수. 5회 도달 판정 기준 |
| 직전 분해 결과 | 마지막 분해 턴의 `items`. 재구성의 기준이 되며 매 분해 턴마다 갈아 끼운다 |
| 대화 턴 | 사용자 발화와 서버 응답 문구. 질문 턴은 제시한 선택지를 함께 남긴다 |

- **모델이 보는 것은 이 상태를 재구성한 하나의 입력이다.** 대상, 있으면 직전 분해
  결과, 그다음 대화 순서로 싣는다.
- **지시문에는 사용자 입력을 싣지 않는다.** 개인정보 마스킹은 모델 입력 본문에만
  적용되므로, 대상·발화가 지시문으로 새면 원문 그대로 provider에 전달된다.
- 남은 질문 횟수를 지시문에 알려 모델이 스스로 분해로 넘어가게 하고, **질문 5회에
  도달했거나 `instruction`이 있으면 모델이 질문을 반환해도 서버가 분해 턴으로
  처리한다.** `instruction`은 세션에 남으므로 이어지는 턴에서도 질문이 나가지 않는다.

### 2.5 헤더와 오류

- `Idempotency-Key`는 시작·이어가기 모두에서 선택 헤더다. 같은 키의 재시도는 저장된
  성공 응답을 그대로 받으므로, 시작 요청의 재시도가 세션을 중복 생성하지 않는다.
  헤더가 없거나 공백이면 매번 새로 실행한다.
- 시작 요청이 모델 호출에서 실패하면 세션 식별자만 남고 쪼개기 시작 기록은 없다.
  그 세션으로 이어가기를 호출하면 `404`다.

| status | 언제 |
| --- | --- |
| `404` | 없는 세션, TTL 만료, UUID 형식이 아닌 `sessionId`, 쪼개기 시작 기록이 없는 세션 |
| `422` | `target.title`·`message`가 공백이거나 길이 제한을 넘긴 요청 |
| `429` | 세션 수·대화 크기·멱등 캐시·rate limit 등 프로세스 보호 한도 초과 |
| `503` | provider 설정 누락·호출 실패, 스키마를 벗어난 모델 응답, `items`가 비어 있는 분해 턴 |

본문 형식은 `docs/specs/17-spring-compatible-http-base.md`의 공통 오류 계약을 따른다.

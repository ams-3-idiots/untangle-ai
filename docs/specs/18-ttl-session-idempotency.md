# TTL 인메모리 세션과 중복 요청 방지

> 관련 GitHub Issue: [#18](https://github.com/ams-3-idiots/untangle-ai/issues/18)

## 1. 핵심 결정

- 세션·대화·멱등 응답은 DB 없이 프로세스 메모리에만 보관한다.
- 세션은 **마지막 성공 요청 후 30분** 유지하고, 세션을 사용하는 요청이 성공할
  때마다 수명을 갱신한다.
- 만료된 세션, 발급된 적 없는 세션, 프로세스 재시작·배포로 사라진 세션은 모두
  같은 `404`로 응답한다.
- 세션 소유권 검사는 없다 — 사용자 개념이 없으므로 `sessionId` 자체가 접근
  자격이다.
- 멱등 캐시는 `Idempotency-Key`별로 구분하며 마지막 사용 후 30분 보관한다
  (Spring은 user+key 스코프, 기록 후 10분).
- 같은 `Idempotency-Key`의 요청이 동시에 들어오면 하나만 실행하고 나머지는
  그 실행 결과를 공유한다.
- 사용자별 사용량 쿼터는 제거한다 — 프로세스 단위 보호 한도로 대체한다.

## 2. 상세 설계

### 2.1 세션 저장소와 수명

세션 저장소는 다음 동작을 제공한다.

- 생성: 새 `sessionId`, 대화 상태와 만료 시각을 프로세스 메모리에 저장한다.
- 조회: 만료되지 않은 세션의 대화 상태를 반환한다.
- 갱신: 세션을 사용하는 요청이 성공한 경우에만 대화 상태를 저장하고 만료 시각을
  요청 완료 시점부터 30분 뒤로 갱신한다.
- 정리: 만료된 세션을 메모리에서 제거한다.

세션은 프로세스 메모리에만 존재하며, 마지막 성공 요청 후 30분이 지나면 만료된다.

만료된 세션, 발급된 적 없는 세션, 프로세스 재시작·배포로 사라진 세션은 모두
동일한 `404` ProblemDetail로 처리한다. 실패한 요청은 세션의 대화 상태와 만료
시각을 갱신하지 않는다.

쪼개기 대화의 시작 기록, 질문·답 이력과 직전 분해 결과를 세션에 보관하고 다음
턴에서 복원한다.

### 2.2 Idempotency-Key

LLM을 호출하는 3개 경로(덤프, 쪼개기 시작·이어가기)에서 사용한다.
세션 생성은 LLM을 호출하지 않으므로 대상이 아니다.

- 선택 헤더다. 없거나 공백이면 멱등 처리를 우회한다(재시도가 매번 LLM을
  호출한다).
- 값 형식은 검증하지 않는다 — 비공백 문자열이면 수용한다. 앱 생성 UUID를
  권장한다.
- 성공 응답만 캐시한다.
- 같은 키의 요청이 동시에 들어오면 먼저 들어온 요청만 LLM을 호출한다. 나머지
  요청은 첫 요청이 완료될 때까지 기다린 뒤 같은 응답을 반환한다.
- 먼저 들어온 요청이 실패하면 오류를 기다리던 요청에도 전달하고 결과는 캐시하지
  않는다. 이후 같은 키로 재시도하면 요청을 다시 실행한다.
- 요청 본문은 비교하지 않는다 — 같은 키에 다른 본문을 보내면 이전 응답이
  재전송된다. 내용이 다른 새 요청은 반드시 새 키를 쓴다.
- 캐시 항목은 마지막 사용 후 30분 동안 보관하고, 만료되면 메모리에서 제거한다.

### 2.3 설정과 보호 한도

다음 항목을 애플리케이션 설정으로 관리한다.

| 설정 항목 | 환경 변수 | 기본값 | 측정 기준 |
| --- | --- | --- | --- |
| 세션 TTL | `SESSION_TTL_SECONDS` | 1800 (30분) | 마지막 성공 요청 이후 경과 시간 |
| 멱등 응답 캐시 TTL | `IDEMPOTENCY_TTL_SECONDS` | 1800 (30분) | 캐시 항목의 마지막 사용 이후 경과 시간 |
| 최대 세션 수 | `MAX_SESSIONS` | 1000 | 만료되지 않은 세션 수 |
| 세션별 최대 턴 수 | `MAX_SESSION_TURNS` | 50 | 세션에 저장된 사용자 발화와 서버 응답의 턴 수 |
| 세션별 최대 대화 크기 | `MAX_SESSION_CONVERSATION_CHARS` | 50000 | 세션에 저장된 대화 문자열의 문자 수 |
| 최대 멱등 응답 캐시 수 | `MAX_IDEMPOTENCY_ENTRIES` | 1000 | 만료되지 않은 성공 응답과 실행 중인 요청의 수 |
| rate limit 요청 수 | `RATE_LIMIT_REQUESTS` | 60 | 시간 구간 안에 프로세스가 받은 LLM 요청 수 |
| rate limit 시간 구간 | `RATE_LIMIT_WINDOW_SECONDS` | 60 | 요청 수를 세는 구간의 길이(초) |

- 용량 상한을 검사하기 전에 만료된 세션과 캐시 항목을 먼저 정리한다.
- 세션·대화·응답 캐시 또는 rate limit을 초과하면 `429` ProblemDetail로
  응답한다.

# TTL 인메모리 세션과 중복 요청 방지

> 관련 GitHub Issue: [#18](https://github.com/ams-3-idiots/untangle-ai/issues/18)

구현 전 초안이다. 구현 과정에서 확정한 내용을 이 문서에 반영한다.

## 1. 핵심 결정

- 세션·대화·멱등 응답은 DB 없이 프로세스 메모리에만 보관한다.
- 세션은 **마지막 성공 요청 후 30분** 유지하고, 세션을 사용하는 요청이 성공할
  때마다 수명을 갱신한다.
- 만료된 세션, 발급된 적 없는 세션, 프로세스 재시작·배포로 사라진 세션은 모두
  같은 `404`로 응답한다.
- 세션 소유권 검사는 없다 — 사용자 개념이 없으므로 `sessionId` 자체가 접근
  자격이다.
- 멱등 캐시는 `Idempotency-Key` 단독 스코프이며 마지막 사용 후 30분 보관한다
  (Spring은 user+key 스코프, 기록 후 10분).
- 사용자별 사용량 쿼터는 제거한다 — 프로세스 단위 보호 한도로 대체하고 `429`
  계약은 유지한다.

## 2. 상세 설계

### 2.1 세션 수명

- 세션은 프로세스 메모리에만 존재한다. 마지막 성공 요청 후 30분이 지나면
  만료되며, 세션을 사용하는 요청이 성공할 때마다 수명이 갱신된다.
- 쪼개기 대화(시작 기록, 질문·답 이력, 직전 분해 결과)는 서버가 세션에
  보관하고 다음 턴에서 복원한다.

### 2.2 Idempotency-Key

LLM을 호출하는 3개 경로(덤프, 쪼개기 시작·이어가기)에서 사용한다.
세션 생성은 LLM을 호출하지 않으므로 대상이 아니다.

- 선택 헤더다. 없거나 공백이면 멱등 처리를 우회한다(재시도가 매번 LLM을
  호출한다).
- 값 형식은 검증하지 않는다 — 비공백 문자열이면 수용한다. 앱 생성 UUID를
  권장한다.
- 성공 응답만 캐시한다. 같은 키의 재요청은 LLM을 다시 호출하지 않고 저장된
  응답 본문을 그 경로의 성공 상태 코드로 재전송한다.
- 오류 응답(`404`·`422`·`429`·`503`)은 캐시하지 않는다 — 같은 키로 재시도하면
  다시 실행한다.
- 요청 본문은 비교하지 않는다 — 같은 키에 다른 본문을 보내면 이전 응답이
  재전송된다. 내용이 다른 새 요청은 반드시 새 키를 쓴다.
- 캐시 항목은 마지막 사용 후 30분 보관한다. 크기 상한과 정리 정책은 구현에서
  정한다.

### 2.3 보호 한도

- DB 없이 동작하는 rate limit과 세션 수·턴 수·대화 크기·멱등 캐시 크기 상한을
  둔다. 구체적인 값과 측정 기준은 구현에서 정한다.
- 어떤 보호 한도든 초과 시 응답은 `429` ProblemDetail 하나로 통일한다.

### 2.4 호환성 테스트 사례

| ID | 시나리오 | 기대 결과 |
| --- | --- | --- |
| T-01 | 발급된 적 없는 UUID로 덤프·이어가기 | `404` ProblemDetail (`title: "Not found"`) |
| T-02 | 마지막 성공 요청 후 30분 경과한 세션 사용 | `404` |
| T-03 | 30분 이내 성공 요청으로 세션 수명 갱신 | 갱신 이후 30분까지 사용 가능 |
| T-04 | 저장소 초기화(재시작 시뮬레이션) 후 기존 세션 사용 | `404` |
| T-05 | 같은 `Idempotency-Key`로 같은 요청 2회 | 본문 동일, LLM 호출 1회, 성공 상태 코드는 경로 고유 값 유지(시작 `201`, 덤프·이어가기 `200`) |
| T-06 | 다른 키로 2회 | LLM 2회 호출, 독립 응답 |
| T-07 | 키 없이 2회 | 캐시 미사용 — LLM 2회 호출 |
| T-08 | 1회차가 `503`으로 실패한 뒤 같은 키로 재시도 | 오류는 캐시되지 않아 재실행 |
| T-09 | 보호 한도(rate limit 등) 초과 | `429` ProblemDetail (`title: "Too many requests"`) |
| T-10 | 멱등 캐시 항목의 마지막 사용 후 30분 경과, 같은 키 재요청 | 캐시 만료 — 재실행 |

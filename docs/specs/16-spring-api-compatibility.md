# Spring 호환 AI API 통신 계약과 호환성 기준

> 관련 GitHub Issue: [#16](https://github.com/ams-3-idiots/untangle-ai/issues/16)

Spring 서버의 브레인덤프와 할 일 쪼개기를 FastAPI로 이전([#10](https://github.com/ams-3-idiots/untangle-ai/issues/10))할 때
모바일 앱이 요청 경로와 요청·응답 DTO를 바꾸지 않고 쓸 수 있도록, 지원 API의
통신 계약과 호환성 기준을 이 문서 한 곳에서 확정한다. 후속 구현 이슈
#17, #18, #19, #20, #21, #22는 이 문서를 공통 기준으로 사용한다.

이 문서는 앱이 관찰할 수 있는 HTTP 계약(경로·헤더·본문·상태 코드·오류)만
확정한다. 저장소 구조, LLM 클라이언트 설계 같은 내부 구현은 각 후속 이슈에서
정한다.

## 1. 핵심 결정

### 1.1 호환성 기준의 정본은 Spring 코드와 모바일 계약 문서다

| 출처 | 역할 |
| --- | --- |
| Spring 서버 코드 (`../server`, develop 최신) | 실제 동작의 정본 |
| `../server/docs/mobile-api-contract.md` | 앱 온보딩용 계약서 — 앱이 이 문서를 보고 구현한다 |

- Android·iOS 앱은 아직 착수 전이라(로컬 워크스페이스에서 앱 코드 0건 확인,
  2026-08-12 기준) 앱의 실제 호출 코드는 존재하지 않는다. 따라서 앱이 의존할
  계약의 기준은 위 두 출처다.
- 두 출처가 서로 다르면 **양쪽을 모두 만족하는(더 엄격한) 계약을 채택**한다.
  발견된 불일치와 채택 결정은 [2.8](#28-spring-문서코드-불일치와-채택-결정)에 정리한다.

### 1.2 유지하는 계약

앱을 변경하지 않기 위해 다음을 Spring과 동일하게 유지한다. 상세 값은 2장에 있다.

| 항목 | 내용 |
| --- | --- |
| 경로·메서드·성공 코드 | 지원 4개 경로, 모두 POST, 세션 생성·쪼개기 시작은 `201`, 덤프·쪼개기 이어가기는 `200` |
| 요청·응답 DTO | 와이어 필드 이름(camelCase), 필수 여부, 길이·개수 제한을 Spring과 동일하게 유지 |
| `TaskDraft` | 8개 필드 전부 직렬화, 기능별 null 의미 유지 ([2.4](#24-taskdraft-계약)) |
| `proposalId == sessionId` | 모든 응답에서 두 값은 항상 같다 (로깅·식별용) |
| 오류 본문 | RFC 9457 ProblemDetail (`type`, `title`, `status`, `detail`) |
| 오류 상태 코드 | `404`(세션 없음·만료), `422`(요청 형식 검증 실패), `429`(과다 요청), `503`(외부 AI 실패) |
| `Idempotency-Key` | 같은 키 재요청은 LLM을 다시 호출하지 않고 같은 응답을 재전송 |
| `X-Request-Id` | 유효한 요청 값은 에코, 없거나 무효면 생성 — 모든 응답 헤더에 존재 |
| 업무 규칙 상한 | 결과 최대 5개, 쪼개기 질문 최대 5회, 질문 선택지 2~4개 |
| 정상 빈 결과 | 덤프 `tasks: []`는 오류가 아닌 정상 응답, `assistantText`로 재입력 유도 |
| 개인정보 처리 | 앱은 원문을 그대로 보내고, 응답에서는 마스킹 없이 원문이 복원되어 온다 |

### 1.3 제거하는 계약

다음은 새 AI 서버가 제공하지 않는다. 모두 상위 이슈 #10의 결정을 따른다.

| 항목 | Spring 동작 | 새 AI 서버 | 앱 관점 영향 |
| --- | --- | --- | --- |
| JWT 인증 | access token 검증, 실패 시 `401` | `Authorization` 헤더를 허용하되 검증·식별에 쓰지 않음. **`401`을 반환하지 않는다** | AI 경로에서 토큰 갱신 인터셉터가 발동할 일이 없어진다. 기존 앱 로직은 그대로 두어도 무해 |
| 세션 소유권 | 타인 세션 접근 시 `404` (소유자 검사) | 사용자 개념이 없어 소유권 검사 없음 — `sessionId`(UUID) 자체가 접근 자격 | 동일하게 "모르는 세션 = `404`"로 관찰됨 |
| `single-add` | `POST /api/v1/ai-sessions/{sessionId}/single-add` | 미제공 (`404`) | 이 기능은 서비스에서 제외됨 |
| `suggest` | `POST /api/v1/ai-sessions/{sessionId}/suggest` | 미제공 (`404`) | 이 기능은 서비스에서 제외됨 |
| `report` | `POST /api/v1/report` | AI 서버 범위 밖 — 기존 Spring 서버에 남는다 | 공개 진입점 라우팅이 AI 경로만 FastAPI로 분기 (#10 참고 사항) |
| 사용자별 사용량 쿼터 | 사용자별 토큰 쿼터(24시간·30일 롤링) 초과 시 `429` | 사용자 개념이 없어 사용자별 쿼터 없음. 프로세스 단위 보호 한도(#18)로 대체 | `429` 계약 자체는 유지 ([2.3](#23-공통-오류-계약)) |
| 영구 저장 | 세션·대화를 DB에 저장 (대화 원문은 365일 롤링 파기) | 프로세스 인메모리, 마지막 성공 요청 후 30분 유지 | 30분 초과·서버 재시작 시 `404` — 앱의 기존 `404` 처리(새 세션 생성 후 재시도)로 흡수 |

### 1.4 새로 정의하는 동작

Spring과 다르게 동작하지만 계약 문서(`mobile-api-contract.md`)가 앱에 약속한
범위는 깨지 않는 항목이다.

| 항목 | Spring | 새 AI 서버 | 근거 |
| --- | --- | --- | --- |
| 세션 수명 | TTL 없음 (대화 원문만 365일 파기) | **마지막 성공 요청 후 30분** (성공 요청마다 갱신). 만료·재시작 시 `404` | #10 핵심 결정 |
| 멱등 캐시 수명 | user+key 스코프, 기록 후 10분 | **키 단독 스코프, 마지막 사용 후 30분** — 사용자 개념이 없고, 키가 앱 생성 UUID라 충돌 위험을 수용 | #10 핵심 결정, 상한은 #18 |
| 질문 상한 강제 | 프롬프트 지시 수준 (구조적 차단 없음) | **서버가 구조적으로 강제** — 질문 턴 5회 도달 후에는 반드시 분해 턴을 반환 | [2.8](#28-spring-문서코드-불일치와-채택-결정) 항목 6 |
| LLM provider | Anthropic Claude | **OpenAI structured output** — 응답 계약은 동일 유지 | #10 핵심 결정, 구현은 #19 |
| 검증 실패 본문 | Spring ProblemDetail | FastAPI 기본 `422` 본문(`{"detail": [...]}`)을 쓰지 않고 **ProblemDetail로 변환** | 구현은 #17 |

### 1.5 오류 응답 원칙

- 지원 경로의 모든 오류 응답 본문은 RFC 9457 ProblemDetail로 통일한다.
- `422`는 요청 형식(타입·필수값·길이) 검증 실패 전용이다. 업무 규칙 위반을
  `422`로 표현하지 않는다(개발 가이드라인 상시 규칙과 동일).
- 도메인 오류는 `404`(세션 없음·만료), `429`(보호 한도 초과), `503`(외부 AI
  실패)에 매핑한다. 현행 FastAPI가 쓰는 `400`·`502`는 지원 경로 계약에서 쓰지
  않는다.
- 앱은 **상태 코드로만 분기**한다. `title`·`detail` 문구는 사람이 읽는 참고
  정보이며 정확한 문자열은 계약이 아니다.

## 2. 상세 설계

### 2.1 지원 경로와 상태 코드

| 메서드 | 경로 | 성공 코드 | 요청 본문 | 응답 본문 |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/ai-sessions` | `201` | 없음 | `{"sessionId": "<uuid>"}` |
| POST | `/api/v1/ai-sessions/{sessionId}/dump` | `200` | 덤프 요청 ([2.6](#26-브레인덤프-api)) | 덤프 응답 |
| POST | `/api/v1/ai-sessions/decompose` | `201` | 쪼개기 시작 요청 ([2.7](#27-할-일-쪼개기-api)) | 쪼개기 응답 |
| POST | `/api/v1/ai-sessions/{sessionId}/decompose` | `200` | 쪼개기 이어가기 요청 | 쪼개기 응답 |

- 위 4개가 새 AI 서버의 공개 계약 전부다. 그 외 경로(`single-add`, `suggest`,
  기존 FastAPI `/api/v1/ai/**` 포함)는 라우터에 등록하지 않으며 `404`가 된다.
  계약 밖 경로의 `404` 본문 형식은 보장하지 않는다.
- 경로의 `{sessionId}`가 UUID 형식이 아니면 발급된 적 없는 식별자이므로
  "세션 없음"과 동일하게 `404`로 처리한다. `422`(형식 검증)는 요청 본문 전용으로
  남긴다.

### 2.2 공통 헤더 규칙

#### Authorization

- 헤더가 있어도, 없어도, 값이 무엇이어도 요청 처리 결과가 달라지지 않는다.
- JWT 검증·사용자 식별에 사용하지 않으며 로그에도 남기지 않는다.
- 새 AI 서버는 어떤 경우에도 `401`·`403`을 반환하지 않는다.

#### Idempotency-Key

LLM을 호출하는 3개 경로(덤프, 쪼개기 시작·이어가기)에서 사용한다.
세션 생성은 LLM을 호출하지 않으므로 대상이 아니다.

- 선택 헤더다. 없거나 공백이면 멱등 처리를 완전히 우회한다(재시도가 매번 LLM을
  호출한다).
- 값 형식은 검증하지 않는다 — 비공백 문자열이면 수용한다. 계약 문서는 앱 생성
  UUID를 권장한다.
- **성공 응답만 캐시한다.** 같은 키의 재요청은 LLM을 다시 호출하지 않고 저장된
  응답 본문을 그 경로의 성공 상태 코드로 재전송한다.
- 오류 응답(`404`·`422`·`429`·`503`)은 캐시하지 않는다 — 같은 키로 재시도하면
  다시 실행한다. 계약 문서의 "`503`은 같은 키로 재시도 가능"이 이 규칙에 기댄다.
- 요청 본문은 비교하지 않는다. 같은 키에 다른 본문을 보내면 이전 응답이
  재전송된다(내용이 다른 새 요청은 반드시 새 키 — 계약 문서와 동일).
- 캐시 항목은 마지막 사용 후 30분 보관한다(같은 키가 재사용되면 갱신 — #10의
  "멱등 응답은 마지막 요청 후 30분 보관"을 따른다). 크기 상한과 정리 정책은
  #18에서 정한다.

#### X-Request-Id

- 요청 헤더 값이 `[A-Za-z0-9._-]{1,64}` 패턴에 맞으면 그대로 사용하고, 없거나
  패턴을 벗어나면 서버가 UUID를 생성한다.
- 결정된 값은 **모든 응답(오류 포함)의 `X-Request-Id` 헤더**에 싣고, 서버 로그의
  요청 추적 식별자로 쓴다.

### 2.3 공통 오류 계약

모든 오류 본문은 RFC 9457 ProblemDetail이다. `Content-Type`은
`application/problem+json`을 사용한다(Spring 쪽은 프레임워크 기본 동작에 기댄
것으로 코드상 명시 근거는 없다 — 앱은 미디어 타입이 아니라 상태 코드로
분기한다).

```json
{ "type": "about:blank", "title": "Not found", "status": 404, "detail": "ai session not found: cace6837-…" }
```

| status | title | 언제 | detail |
| --- | --- | --- | --- |
| `404` | `Not found` | 없는 세션, TTL 만료, 재시작으로 소실, UUID 형식이 아닌 `sessionId`, 쪼개기 시작 기록이 없는 세션에 이어가기 호출 | 세션 식별자를 포함할 수 있음 |
| `422` | `Validation failed` | 요청 본문의 타입·필수값·길이 검증 실패 | `"필드경로: 사유"`를 `"; "`로 연결한 문자열 (필드 경로는 요청 본문 기준, 예: `"text: must not be blank"`) |
| `429` | `Too many requests` | 보호 한도 초과 (rate limit, 세션 수·턴 수 상한 등 — 값은 #18) | 사유 요약 |
| `503` | `AI service unavailable` | provider 설정 누락, timeout·네트워크·SDK 호출 실패, 스키마를 벗어난 모델 응답, 사용 가능한 결과가 없는 모델 응답 | 재시도 안내 문구 (고정) |

- `type`은 항상 `"about:blank"`이다. `status`는 HTTP 상태 코드와 같은 값이다.
- `title`은 위 표의 고정 문자열을 유지한다. 단 앱 분기 기준은 상태 코드다.
- `detail`에 사용자 입력·대화·프롬프트·모델 원문·스택 트레이스를 넣지 않는다.
- Spring의 `401`(인증 실패)과 `429` 중 사용자별 토큰 쿼터 사유는 새 서버에
  존재하지 않는다 ([1.3](#13-제거하는-계약)).

### 2.4 TaskDraft 계약

덤프의 `tasks[]`와 쪼개기의 `items[]`가 공유하는 할 일 제안 DTO다.
**8개 필드는 값이 없어도 키를 생략하지 않고 `null`로 직렬화한다.**

| 필드 | 타입 | null 의미 |
| --- | --- | --- |
| `title` | string | null·빈 문자열 없음 — 비공백이 보장된다 |
| `memo` | string \| null | 보충 메모 없음 |
| `importance` | int(1\|2\|3) \| null | 미지정 (1=높음, 2=중간, 3=낮음) |
| `estimatedMinutes` | int(>0) \| null | 예상 소요 시간 단서 없음 |
| `dueDate` | string(`yyyy-MM-dd`) \| null | 마감 날짜 단서 없음 |
| `dueTime` | string(`HH:mm`) \| null | 마감 시각 단서 없음 |
| `reminderMinutesBefore` | int(10\|30\|60\|180\|1440) \| null | 알림 없음 |
| `sourceExcerpt` | string \| null | 추출 근거 원문 없음 |

서버는 모델 출력을 그대로 내보내지 않고 다음 정규화를 거친다(Spring과 동일).

- 제목이 공백뿐인 항목은 버린다.
- 제목의 `strip + 소문자` 결과가 같으면 첫 항목만 남긴다(순서 유지).
- `importance`가 1~3 밖이면 null, `estimatedMinutes`가 0 이하면 null,
  `reminderMinutesBefore`가 허용값 밖이면 null로 바꾼다.
- 빈 문자열 `memo`·`dueDate`·`dueTime`은 null로 바꾼다.

기능별 고정 규칙:

| 필드 | 덤프 | 쪼개기 |
| --- | --- | --- |
| `memo` | 모델 제안 (없으면 null) | **항상 null** |
| `dueDate`·`dueTime` | 모델 제안 (`clientNow` 기준 환산) | **항상 null** |
| `reminderMinutesBefore` | 모델 제안 | **항상 null** |
| `sourceExcerpt` | 입력 `text`의 **부분 문자열임을 서버가 검증** — 아니면 null | **항상 대상 제목** (개행을 공백으로 접고 앞뒤 공백을 없앤 `target.title`) |
| `importance`·`estimatedMinutes` | 모델 제안 — 정규화로 null이 될 수 있음 | 동일 |

계약 문서의 "importance·estimatedMinutes는 덤프·쪼개기에서 항상 제안돼 온다"는
프롬프트 지시이지 코드 보장이 아니다. **계약은 null 허용으로 확정**하며, 앱은
두 필드의 null을 처리해야 한다 ([2.8](#28-spring-문서코드-불일치와-채택-결정) 항목 5).

### 2.5 세션·멱등성·보호 한도

#### 세션 수명

- 세션은 프로세스 메모리에만 존재한다. **마지막 성공 요청 후 30분**이 지나면
  만료되며, 세션을 사용하는 요청이 성공할 때마다 수명이 갱신된다.
- 만료된 세션, 발급된 적 없는 세션, 프로세스 재시작·배포로 사라진 세션은 모두
  같은 `404`로 응답한다 — 앱은 구분할 수 없고 구분할 필요도 없다(새 세션 생성
  후 재시도).
- `POST /api/v1/ai-sessions`는 본문 없이 호출하며 `201`과 새 UUID를 반환한다.
  쪼개기는 시작 API가 세션을 직접 만들어 돌려주므로 별도 생성이 필요 없다.
- 모든 응답의 `proposalId`는 해당 세션의 `sessionId`와 같은 값이다.

#### 세션과 대화 상태

- 쪼개기 대화(시작 기록, 질문·답 이력, 직전 분해 결과)는 서버가 세션에 보관하고
  복원한다. 앱은 이력을 관리하지 않고 **매 턴 이번 발화 하나만** 보낸다.
- 쪼개기 이어가기는 쪼개기 시작으로 만들어진 세션에서만 동작한다. 시작 기록이
  없는 세션(예: `POST /ai-sessions`로 만든 세션)에 이어가기를 호출하면 `404`다
  (Spring과 동일 — [2.8](#28-spring-문서코드-불일치와-채택-결정) 항목 3).
- 덤프는 살아 있는 세션이면 용도 구분 없이 동작한다(Spring과 동일). 같은 세션의
  이전 대화를 프롬프트 맥락으로 쓸지는 계약이 아니며 #20에서 정한다.

#### 보호 한도

- DB 없이 동작하는 rate limit과 세션 수·턴 수·대화 크기·멱등 캐시 크기 상한을
  둔다. 구체적인 값과 측정 기준은 #18에서 정한다.
- 어떤 보호 한도든 초과 시 응답은 `429` ProblemDetail 하나로 통일한다.

### 2.6 브레인덤프 API

`POST /api/v1/ai-sessions/{sessionId}/dump` → `200`

#### 요청

```json
{
  "text": "졸업논문 중간발표가 2주 뒤인데 아직 데이터 정리도 안 했고 …",
  "existingTaskTitles": ["교수님 미팅 준비"],
  "clientNow": "2026-07-09T22:00:00+09:00"
}
```

| 필드 | 필수 | 제약 |
| --- | --- | --- |
| `text` | 필수 | 비공백, 최대 8000자 |
| `existingTaskTitles` | 필수 (빈 배열 허용, null 불가) | 최대 200개, 항목당 최대 500자 |
| `clientNow` | 선택 | 최대 40자. ISO-8601 권장 — 상대 기한("다음 주까지") 환산 기준. 형식 자체는 검증하지 않는다 |

#### 응답

```json
{
  "proposalId": "cace6837-…",
  "tasks": [
    {
      "title": "논문 데이터 정리하기",
      "memo": "중간발표 전까지 완료 필요",
      "importance": 1,
      "estimatedMinutes": 300,
      "dueDate": "2026-07-23",
      "dueTime": null,
      "reminderMinutesBefore": null,
      "sourceExcerpt": "아직 데이터 정리도 안 했고"
    }
  ],
  "assistantText": "일단 눈에 보이는 것부터 나눠봤어요."
}
```

| 필드 | 규칙 |
| --- | --- |
| `proposalId` | 경로의 `sessionId`와 같은 값 |
| `tasks` | `TaskDraft` 배열, **최대 5개**, null이 아님(빈 배열 가능). 중복 제안 방지 기준은 요청의 `existingTaskTitles` |
| `assistantText` | 필드는 항상 존재. `tasks: []`일 때는 비공백이 보장된다(재입력 안내) |

- **`tasks: []`는 정상 `200` 응답이다** (감정·잡담뿐이라 추출 불가). 이때
  `assistantText`가 재입력 안내를 담는다. 결과도 비고 안내문도 없는 모델 응답은
  `503`으로 처리한다.
- 응답의 `sourceExcerpt`는 요청 `text`의 부분 문자열임이 보장된다(아니면 null).
  검증은 마스킹 복원 후의 원문 기준으로 수행한다
  ([2.8](#28-spring-문서코드-불일치와-채택-결정) 항목 7).

### 2.7 할 일 쪼개기 API

- 시작: `POST /api/v1/ai-sessions/decompose` → `201` (세션을 직접 생성해 반환)
- 이어가기: `POST /api/v1/ai-sessions/{sessionId}/decompose` → `200`

#### 시작 요청

```json
{
  "target": { "title": "운동 시작하기", "notes": null },
  "instruction": null
}
```

| 필드 | 필수 | 제약 |
| --- | --- | --- |
| `target` | 필수 | 객체 |
| `target.title` | 필수 | 비공백, 최대 500자 |
| `target.notes` | 선택 | 최대 4000자 |
| `instruction` | 선택 | 최대 2000자. 있으면 질문 없이 바로 분해한다(재쪼개기 등) |

#### 이어가기 요청

```json
{ "message": "체력 증진이 목적이야" }
```

| 필드 | 필수 | 제약 |
| --- | --- | --- |
| `message` | 필수 | 비공백, 최대 2000자 |

#### 응답 (시작·이어가기 공통) — `items`의 null 여부로 턴 구분

```json
{
  "sessionId": "cace6837-…",
  "proposalId": "cace6837-…",
  "items": null,
  "options": ["체중 감량", "체력 증진", "스트레스 해소"],
  "firstStep": null,
  "assistantText": "운동을 시작하려는 주된 목적이 뭔가요?"
}
```

| 필드 | 질문 턴 | 분해 턴 |
| --- | --- | --- |
| `items` | **null** | `TaskDraft` 배열 1~5개, 배열 순서 = 실행 순서 |
| `options` | 선택지 2~4개 | **null** |
| `firstStep` | null | null |
| `assistantText` | AI의 질문 한 문장 | 한두 문장 설명 |
| `sessionId`·`proposalId` | 항상 존재, 같은 값 | 항상 존재, 같은 값 |

- **`firstStep` 필드는 유지하되 값은 언제나 null이다.** '지금 할 첫 단계'는
  `items[0]`으로 온다(계약 문서 §4와 동일). 분해 턴의 `items`가 비어 있는 모델
  응답은 `503`으로 처리한다.
- 질문 턴의 조건: `assistantText`가 비공백이고 중복 제거 후 `options`가 2개
  이상. 선택지는 최대 4개까지만 내려보낸다.
- **질문은 대화 전체에서 최대 5회다.** 질문 턴 5회에 도달하면 이후 응답은
  반드시 분해 턴이다. Spring은 이를 프롬프트로만 지시했지만 새 서버는 구조적으로
  강제한다 ([1.4](#14-새로-정의하는-동작)).
- 분해 턴을 받은 뒤에도 같은 세션에 "더 잘게 쪼개줘"를 보내면 서버가 직전
  목록을 기억하고 전체를 더 잘게 재구성해 돌려준다(항목 수 상한 5개 동일).
- "그냥 쪼개줘"·"모르겠어" 같은 발화에는 즉시 분해로 넘어간다(프롬프트 규칙,
  구현은 #21).
- 이어가기 시 세션이 없거나 만료되었으면 `404`, 쪼개기 시작 기록이 없는
  세션이면 `404`다 ([2.5](#25-세션멱등성보호-한도)).

### 2.8 Spring 문서·코드 불일치와 채택 결정

조사에서 발견한 계약 문서(`mobile-api-contract.md`)와 Spring 코드의 불일치,
그리고 새 서버가 채택하는 계약이다. 지원 범위 밖 기능(suggest 등)의 불일치는
제외했다.

| # | 불일치 | 새 서버의 채택 |
| --- | --- | --- |
| 1 | 문서의 `429` 사유에 월 쿼터 누락 (코드는 30일 롤링 쿼터도 `429`) | 사용자별 쿼터 자체가 제거됨. `429`는 보호 한도 초과 하나로 정의하고 사유 문구는 계약에서 제외 |
| 2 | 문서는 `401`도 ProblemDetail이라 하나 코드상 보장 없음 (Spring Security 기본 처리) | `401` 자체가 없어져 해소 |
| 3 | 문서의 `404` 사유는 "세션 없음·내 세션 아님"뿐이나, 코드는 쪼개기 시작 기록 없는 세션의 이어가기도 `404` | 세 번째 사유를 계약에 명시하고 유지 ([2.3](#23-공통-오류-계약), [2.5](#25-세션멱등성보호-한도)) |
| 4 | 문서는 `Idempotency-Key`를 "UUID"라 하나 코드는 비공백 문자열이면 수용 | 코드 동작(비공백 수용)을 유지하고 UUID는 권장으로 둔다 |
| 5 | 문서는 "importance·estimatedMinutes 항상 제안"이라 하나 코드는 정규화로 null 가능 | **null 허용을 계약으로 확정** — 앱은 두 필드의 null을 처리해야 한다 |
| 6 | 문서는 "질문 최대 5회"라 하나 코드 강제는 프롬프트 수준 | 문서의 약속을 채택하고 **서버가 구조적으로 강제**한다 |
| 7 | 문서는 덤프 `sourceExcerpt`를 "실제 입력의 부분 문자열인지 검증"이라 하나, 코드는 **마스킹된 텍스트 기준**으로 검사해 복원 후에는 경계 사례에서 보장이 깨질 수 있음 | 문서의 약속을 채택 — **마스킹 복원 후의 원문 기준으로 검증**한다 (#20) |

### 2.9 현행 FastAPI 계약과의 차이

현행 FastAPI 서버(#6에서 구현)는 아래 항목이 모두 다르며, 지원 계약으로
대체된다. 기존 경로·DTO·오류 형식의 제거는 #22에서 수행한다.

| 항목 | 현행 FastAPI | 지원 계약 (이 문서) |
| --- | --- | --- |
| 경로 | `POST /api/v1/ai/brain-dump`, `POST /api/v1/ai/task-breakdown` | `/api/v1/ai-sessions/**` 4개 경로 |
| 대화 상태 | 무상태 — 앱이 `clarifications` 이력을 누적 재전송 | 서버가 TTL 세션에 보관 — 앱은 이번 발화만 전송 |
| 와이어 표기 | snake_case (`first_step`) | camelCase (`firstStep`) |
| 응답 구분 | `status` discriminator (`needs_clarification`/`completed`) | `items`의 null 여부로 턴 구분 |
| 결과 DTO | `{title, memo}` 2필드, `memo` 기본 `""` | `TaskDraft` 8필드, 없는 값은 null |
| 오류 본문 | `{"code", "message"}` | RFC 9457 ProblemDetail |
| 오류 상태 | `400`(업무 규칙), `502`(provider·모델 응답), `503`(설정 누락) | `404`/`422`/`429`/`503` — `400`·`502` 미사용 |
| 검증 실패 본문 | FastAPI 기본 `{"detail": [...]}` | ProblemDetail로 변환 |
| 헤더 | 없음 | `Authorization` 허용·무시, `Idempotency-Key`, `X-Request-Id` |
| 질문 상한 | 브레인덤프 1회, 쪼개기 3회 | 브레인덤프는 질문 없음, 쪼개기 최대 5회 |
